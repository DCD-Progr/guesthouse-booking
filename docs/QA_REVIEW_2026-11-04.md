# Reliability review and operations dashboard release

Date: 2026-11-04. Scope: application source, database relationships and RPCs, access rules, auth UI, booking lifecycle, concurrency, dashboard and calendar. This is a bounded engineering verification, not a guarantee of zero defects.

## Changes and findings

- Fixed explicit removal of the single approver designation. Leaving its checkbox unchecked now removes designation for that staff member, including when their role remains approver/admin. Role handover and suspension are checked at request time.
- Rejected blank/null inventory names/codes/destinations and invalid staff inputs at the database API boundary, rather than relying only on forms.
- Prevented a late asynchronous refresh from restoring a workspace after sign-out; added a delayed-response browser regression.
- Isolated approval and personal-request screen state so status filters do not leak between them.
- Rejected null/non-object invitation payloads cleanly. The invitation endpoint still validates the real JWT and current admin role. The privileged key stays in the server environment.
- Pinned resolved dependency versions and split production chunks. No dependencies were upgraded by this release.
- Calendar reservations show traveler names in cells. Request identifiers remain in tooltips for traceability.
- Added role-restricted operations dashboard: exclusive room status categories, guesthouse distribution, 14-day commitments, attention items, arrivals/departures, staff dropdown, date filter and location directory.
- Directory shows confirmed plans, rooms, Break destinations, latest recorded movement and unresolved occupancy. It preserves multiple simultaneous assignments rather than inventing one location. Unknown locations remain explicitly unknown.

## Verification

- Production TypeScript/Vite build.
- 11 unit tests for dates, authentication errors/password setup, dashboard metrics and staff locations.
- 25 database tests, run against PGlite locally and PostgreSQL 17 in CI. Includes all administrative RPC authority checks, RLS, foreign keys, Break uniqueness/protection, allocation consistency, idempotency, room/guesthouse activity, staff designation, decision states, check-in/out/no-show transitions, cancellations and replacement rollback.
- Independent availability oracle: 120 intervals across multiple rooms and closures, checked against a separate interval implementation.
- 20 browser journeys, including desktop and mobile booking, self-approval, inventory/closures, calendar names, dashboard/staff filters, role privacy, invitation/recovery, email throttling, sign-out racing a refresh and 501-record pagination.
- Real PostgreSQL concurrency suite: booking versus booking, booking versus closure, approve versus reject, duplicate approval, ten separate sessions competing for one room, and approval versus cancellation. Exactly one allocation is allowed where capacity is one; cancellation leaves no active slot.
- Live read-only integrity checks: no overlapping slots, confirmed requests without active allocations, wrong-house allocations or missing reservation slots. Operational tables all have RLS enabled. Inventory counts retained.
- Live staff designation mutation tested inside a transaction and rolled back. No live test traveler bookings or staff accounts created by this review.
- Dependency audit: zero known advisories at review time. This is not a claim that undiscovered vulnerabilities cannot exist.
- Visual review at 1440px desktop and 390px mobile. Local Playwright used because the connected browser cannot reach the unpublished workspace server. No document-level horizontal overflow; wide data tables scroll within their containers.

## Dashboard definitions

A room belongs to exactly one category: unresolved occupied, inactive, closure, reservation, available, in that priority order. Break is excluded from physical capacity. The planning chart reflects current reservations, closures and unresolved occupancy, not a predictive model. Pending counts are all currently pending requests in the guesthouse scope; Break count is organization-wide because Break has no guesthouse.

The selected date is a booking-day filter. Latest movement is not GPS or proof of a person's physical position at an arbitrary historical time. Cancelled/replaced records reflect their current state. Actual movement timestamps are retained, but a full historical inventory snapshot and location replay are outside the current model. The interface states these limits.

## Outstanding operational limits

- Production email onboarding/recovery remains constrained by the existing Supabase starter sender. No personal email domain was connected. Non-owner staff invitation delivery and reset acceptance need an approved sender/authentication solution before broad rollout.
- Leaked-password protection is disabled in hosted Auth. Review the feature's plan/availability and enable when available: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection .
- Supabase reports 14 intentional authenticated SECURITY DEFINER entry points. These are the checked write/read API over read-only RLS tables; helpers are not executable by application users. See SECURITY_NOTES.md and https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable .
- Unused-index information notices are expected in a new small installation; capacity and foreign-key indexes were retained.
- Backup/restore disaster-recovery acceptance and high-volume load testing remain outstanding. Tests cover a small installation; global mutation serialization favors correctness over high throughput.
- No realtime subscription is configured. Refresh data retrieves the latest records. Pagination loads every page, but separate concurrent API reads are not a single consistent database snapshot; write decisions are always validated transactionally on the server.
- Self-approval is permitted by the owner's explicit instruction and remains auditable.
